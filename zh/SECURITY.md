## 报告漏洞

**请不要通过公开的 GitHub Issue 报告安全漏洞。**

如果你认为在 Signet 中发现了安全漏洞，请私下向我们报告。我们认真对待所有安全报告，并会及时进行调查。

有两种方式可以报告漏洞：

1. **GitHub 安全公告 (Security Advisories)**：前往仓库的 **Security** 标签页，点击 **Advisories**，然后选择 **Report a vulnerability**。这是首选方式，因为它可以保持讨论私密，并为协作提供一个安全的框架。
2. **电子邮件**：发送邮件至 `contact@crclare.top`。请在邮件主题中注明 "SECURITY"。

### 报告中应包含的内容

为了帮助我们快速分类和修复问题，请包含以下内容：
- 受影响的 Signet 版本。
- 漏洞的描述及其潜在影响。
- 重现该问题的详细步骤。
- 任何概念验证代码或截图（如果适用）。
- 你建议的修复方案（如果有的话）。

## 我们的响应流程

收到报告后，我们将遵循以下流程：

- **确认**：我们将在 72 小时内确认收到你的报告。
- **分类**：我们将调查并确认该问题是否为有效的安全漏洞。
- **修复**：我们将开发补丁并进行彻底测试。
- **披露**：修复准备就绪后，我们将发布安全公告，并为你署名致谢（除非你希望保持匿名）。

## 漏洞范围

Signet 处理诸如用户身份验证、订单绑定和加密授权签发等敏感操作。

### 属于范围内的漏洞

我们特别关注以下类型的漏洞：
- 身份验证或授权绕过（例如，在没有有效 Token 的情况下访问管理路由）。
- 跨站脚本 (XSS)，可以在用户浏览器中执行任意 JavaScript。
- 通过 Cloudflare D1 进行的 SQL 注入。
- 敏感数据暴露（例如，签名密钥、密码哈希或用户电子邮件）。
- 授权签名验证逻辑中的缺陷。
- Webhook 签名绕过（例如，爱发电适配器）。

### 不属于范围内的漏洞

以下情况通常不被视为有效漏洞：
- 拒绝服务 (DoS) 攻击。
- 针对维护者的垃圾信息或社会工程学攻击。
- 需要物理接触用户设备的漏洞。
- 第三方依赖中的问题，且未证明对 Signet 产生实际影响。
- 没有直接安全影响的最佳实践建议（例如，静态资源上缺少 HTTP 响应头）。

## 部署安全最佳实践

如果你正在部署 Signet，请确保：
- 绝对不要将机密信息（`JWT_SECRET`、`LICENSE_SIGN_PRIVATE_KEY` 等）提交到你的仓库中。请使用 Cloudflare Workers Secrets。
- 保持你的 `wrangler` 和依赖项更新。
- 将 `ALLOWED_ORIGIN` 严格配置为你前端对应的域名，在生产环境中避免使用通配符。
